# rfcs/ —— 语义变更提案

ese 的**语义**（而非符号）变更走 RFC 流程。符号表变动不在此列——17 对是硬约束，不接受「再加一个括号」类提案（见 README 参与贡献第 1 条）。

## 什么需要 RFC

| 需要 | 不需要 |
|------|--------|
| 新增关键字、属性、内置函数 | 错别字修正 |
| 修改现有语义（如优先级、作用域规则） | 文档措辞润色 |
| 新增编译目标（如新的 SSR 模式） | 补充示例 |
| 任何**破坏性变更** | 实现代码的内部重构 |

## 流程

```
提案 → 讨论 → 采纳 → 弃用警告 → 破坏
```

1. **提案**：在本目录建 `NNNN-短标题/README.md`（编号四位，递增）。内容须包含六项：**动机 / 语法 / 语义 / 对现有代码的影响 / 是否破坏性 / 迁移方案**。
2. **讨论**：以 Issue 或 PR 评论形式进行。提案状态下编号永久保留，不被复用。
3. **采纳**：合并提案文档，规范文档升次版本。
4. **弃用警告**：涉及破坏性的变更，先在规范里标记为弃用，工具链给出警告。
5. **破坏**：在**下一个次版本**生效，且**必须同时提供迁移工具**（见下）。

## 硬性门槛

> **破坏性变更必须附迁移工具（`ese fmt --migrate` 的一个迁移规则），否则不予受理。**

这条规则是有教训的：按钮定界符从 v2.5 到 v2.8 连续改型四次，每一次都让已写下的历史代码失效。规范化之后，这类改动必须把迁移成本一起交付，而不是推给用户。

## 目录约定

```
rfcs/
├── README.md
├── 0001-按钮定界符空格升级/     ← 已采纳
│   └── README.md
└── 0002-（下一个提案）/
```

已采纳的 RFC 文档**不删除、不修改结论**。若后续被推翻，追加一份说明推翻理由的新文档——被推翻的决定与当时写下的理由同样重要（见规范第二十一节与 README 致谢）。

## 提案模板

```markdown
# RFC NNNN：标题

- 状态：草案 / 讨论中 / 已采纳 / 已拒绝 / 被 NNNN 取代
- 影响版本：规范 vX.Y
- 破坏性：是 / 否

## 动机
（要解决的真实问题，附具体写不出来的代码示例）

## 语法
（新增或修改的文法，附 EBNF 片段）

## 语义
（解析与运行时的确切行为；边界情形如何裁决）

## 对现有代码的影响
（会影响哪些已有写法）

## 迁移方案
（破坏性变更必填：`ese fmt --migrate` 的迁移规则）
```
