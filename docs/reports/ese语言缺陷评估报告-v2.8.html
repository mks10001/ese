ese 语言缺陷评估报告

评估对象：《ese语言规范-完整版》v2.8（含 v1.0 → v2.8 全部规则）。评估方法：逐节走查规范文本，按「术语定义完整性 / 规则可判定性 / 实现可行性 / 生态系统影响」四把尺子筛选可证缺陷，并按影响面与修复成本分级。

规范版本 v2.8 符号表 17 对 实现代码 0 行 评估日期 2026-09-30

总体判断：语言设计已接近收敛，工程实现完全缺席。七轮修订（v2.0 → v2.8）把审美、语法、语义、国际化、词法歧义逐层清完，词法层面已经没有已知的同形构造；但这一版仍然不可运行——没有解析器、没有检查器、没有迁移工具。

本轮走查发现 11 项可证缺陷：5 项 P0（会直接导致真实页面不可用）、6 项 P1（会显著推高使用成本）。其中 10 项已在 v2.9 增量规范中落地解决方案，1 项（实现验证）只能靠写代码解决。

最关键的结论是：纸面迭代的边际收益已经归零。v2.9 之后若继续做纯文档升级，每增加一节规范，未验证假设的存量只会更大。

02P0 缺陷（会导致真实页面不可用）

五项的共性：它们都不是「语言不够优雅」，而是「按现有规范写出来的网站会在真实场景里坏掉」。

P0-1类型契约缺失，拼写错误被静默吞掉 v2.9 已解决

现象
组件属性只有名字和默认值，无类型。调用处写 [< 欢迎卡 名子="张三" >]，规范规定「忽略未知属性」，于是组件拿到的是默认值 "游客"，页面正常渲染、无任何提示。
根因
v2.2 把「属性缺省兜底」定为宽容策略，但没给「显式收紧」留出口——宽容成了唯一行为。
后果
最典型的低代码故障：界面不报错但数据不对，排查成本极高。类型标注同时是组件的事实文档。
建议
属性支持类型标注（文字／数字／是否／名单／字典）与 必须 修饰；ese check 对「未知属性名」「类型不符」「缺必填」分别报错或警告。宽容仍是默认，严格按属性逐项打开。

P0-2无错误边界：一处错误 = 整页白屏 v2.9 已解决

现象
严格级错误的处理是「立即终止」。若页面里 {用户.名字} 的 用户 缺一个键，整页渲染中断——首屏白屏。
根因
v2.2 把「计算错误即停」当作简洁性的代价，但没有配套的局部降级机制。
后果
对一个「中文低门槛、面向初次建站者」的语言来说，这是致命体验问题：用户看到白屏却不知道从哪一行改。
建议
不引入 try/catch 语法，改为容器属性式错误边界：[+ 容错 兜底="数据加载失败" … +]，把降级范围交给用户显式声明，粒度可细到单个组件；同时补安全取值 取(字典, 键, 缺省)。错误仍写日志，不静默。

P0-3事件绑定不能传参，列表交互写不出来 v2.9 已解决

现象
绑定只有 调用 名字，执行块也不能声明形参。于是「删除第 3 行」「加购这件商品」这类最常见的列表操作无法表达——执行块不知道是哪一项触发了它。
根因
v2.1 定「命名触发器」方案时只解决了「按钮 → 逻辑」的绑定，没有解决「哪一条数据」。
后果
商品列表、待办清单、购物车这三类教学与商业场景全部落空，而它们恰好是低代码赛道的主战场。
建议
执行块支持形参 [> 加购(编号) : … >]，绑定处传参 调用 加购({项.id})；并提供事件对象 事件.值 / 事件.索引 / 事件.项 / 事件.目标。

P0-4遍历无键，重渲染丢输入焦点 v2.9 已解决

现象
[~ 遍历 … ~] 没有身份标识。在循环里放输入框（如「批量填价格」），任一状态变更触发重渲染后，正在输入的光标会跳走、已输入内容可能错位。
根因
数据变更采用「引用即全量刷新」，没有把「节点身份」这一概念引入语言。
后果
表单类页面几乎不可用；这是所有声明式框架都踩过、并在早期就修掉的坑。
建议
遍历增加 键={项.id}（key）；无键时保持 v2.8 行为（按序号重渲染），有键时按身份复用节点。ese check 对「循环内含输入框却无键」给警告。

P0-5没有诊断规范，工具链无法开工 v2.9 已解决

现象
规范只给了错误文本的示例，没有错误码、没有诊断数据结构、没有消息来源约定。于是解析器、ese check、编辑器插件、文档四方各自发明一套错误信息。
根因
前七轮修订全部聚焦「语言能不能表达」，未定义「工具怎么说话」。
后果
这是工具链路线的隐性阻塞点：错误码不定，ese check 的验收标准「错配能报准确行号」就无法被机器校验；双语项目还会出现中英错误消息手工维护两份的长期负担。
建议
以 ESE1xxx（词法／语法）、ESE2xxx（静态检查）、ESE3xxx（运行时）、ESE4xxx（构建工具）分段；统一诊断对象（code／severity／file／line／column／message／hint）；消息模板进 diagnostics.json 单一数据源，报错语言跟随文件模式。

03P1 缺陷（显著推高使用成本）

缺陷说明处置
无派生值（computed） 「总价 = 单价 × 数量」只能写成手动的赋值语句并自己保证调用时机，极易漏更新；大页面会把状态同步写成一团。 v2.9 已解决
模块无命名空间、无清单文件 引入只按名字，两个模块定义同名组件时无解；也没有包管理入口。ese.json 缺失使「构建单元的根」无法被工具确定。 v2.9 部分解决
样式表达力不足 属性只有宽／居中／背景／间距。真实设计（圆角、字号层级、间距节奏）做不出来，语言的「画得出真网站」承诺会打折。 v2.9 已解决
可访问性缺位 媒体块无替代文本、输入框无标签关联。既是合规风险，也让生成的页面在无障碍环境下不可读——对学生用户还是教学事故。 v2.9 已解决
无法生成 API 文档 组件与属性只能靠人读源码。组件库一上规模，文档就与实现脱节——这是 Pug 类工具退化成「少数人玩具」的前兆。 v2.9 已解决
破坏性修订无迁移工具 按钮定界符在 v2.5 / v2.6 / v2.7 / v2.8 四版内改了四次，每次都是「用户自己改代码」。这是规范史上最大的工程债。 v2.9 已解决

04P2 缺陷（本轮未处置，需后续跟进）

缺陷说明建议时机
语言从未被实现验证 ★ v2.0 → v2.9 九轮修订产出约十份文档、零行可运行代码。所有「语法可行性」「性能」「易用性」判断均为纸面推断，未经任何反例检验。 立即（最高优先级）
性能模型未定义 「赋值即刷新」是全量重渲染还是有 diff？没有批量更新、没有脏标记约定。页面规模一大，行为不可预期。 解释器 v0.2 同期
无源映射（sourcemap） 产物是 HTML + JS，运行时错误行号指向产物而非 .bd。没有源映射，报错体验会断裂。 解释器 v0.1 同期
SSR 水合细节留白 运行时选型、产物形态、状态序列化、水合粒度均未定。编译模型章节只有原则，没有可实现的契约。 解释器 v0.2
测试表达力偏薄 只有「名称 + 表达式断言」，没有渲染结构断言、快照测试、组件行为测试。组件库无法被回归保护。 v2.10（实现倒逼）
治理流程停留在文档 RFC 冻结流程、单一数据源、弃用周期目前只是本文档里的几段话；仓库尚不存在，无从执行。 开源发布同期

05历史包袱：四次破坏性修订的复盘

按钮定界符的演变是这份规范最有价值的教训样本——它展示了一个「局部最优解」是如何被连续追求到第四次的。

版本形态当时的理由遗留问题
v2.0 – v2.4[( 文字 )]与草案一致的圆括号直觉与「单元素列表含括号表达式」同形
v2.5[( 文字 )] + 位置裁决靠语句／值位置互斥消歧，零成本按钮文字不能含半角 )；同形仍在
v2.6[(( 文字 ))]双圆括号避开常用同形极端同形 [((x))] 只是被推深一层
v2.7[c.文字.c]换字母加点号，与列表「完全不同源」与点语法 c.a.c 在极端构造下同形
v2.8[c. 文字 .c]空格升格为语法成份，同形彻底消灭代价：点语法必须紧贴，值位置不能写松散点语法

三点结论

  1. 前三次修的是症状，第四次修的是根因。v2.5 到 v2.7 都在「把冲突推深一层」，只有 v2.8 换掉了「同源」这个前提。识别「这是同一类冲突的第几次复现」比每次单独找解更重要。
  2. 每次破坏都必须付迁移成本。四次改型累加到用户侧就是四轮手工改动；ese fmt --migrate 不是锦上添花，而是这笔债的最低还款额。
  3. 冻结流程要早于第一次破坏。v2.9 把「破坏性变更必须附迁移工具 + 走 RFC」写进规范，属于事后补课——但比不补好。

06优先级矩阵

高影响 · 低成本 → 立刻做

  • 诊断规范与错误码（P0-5）
  • 安全取值 取 / 取或（P0-2 的一半）
  • 可访问性属性（P1）
  • ese fmt --migrate（P1，纯文本改写）

高影响 · 高成本 → 排进里程碑

  • 属性契约与静态校验（P0-1）
  • 容错容器与边界语义（P0-2）
  • 事件传参与事件对象（P0-3）
  • 遍历键与重渲染策略（P0-4）

低影响 · 低成本 → 顺手做

  • ese.json 清单
  • 文档注释与 ese doc
  • 模块命名空间
  • 样式白名单

低影响 · 高成本 → 推迟到实现反馈

  • SSR 水合细节与运行时选型
  • 性能模型（diff 与批量更新）
  • 测试表达力扩展
  • 完整类型系统（结构体／泛型）

07行动建议（按执行顺序）

  1. 停止纸面升级。v2.9 之后的下一次规范修订，应当由解释器第一行代码或第一个解析失败案例倒逼产生，而非再由评估报告驱动。九轮文档迭代已经把「能想到的问题」基本想完。
  2. 先做 ese fmt --migrate 与 ese check，再写解释器。迁移工具是纯文本改写，工作量最小但消灭历史债；检查器能立刻验证文法是否真的可判定——它是最便宜的「文法正确性测试」。
  3. keywords.json 与 diagnostics.json 必须先落地。这两个文件是解析器、检查器、文档、编辑器插件的共同上游。先有数据源，工具才不会各写一套。
  4. VSCode 插件与检查器同期发布。它同时解决两个问题：中文标点输入的痛点，以及「写完不知道对不对」的反馈真空。
  5. 把「可运行的最小站点」定为 v3.0 的门槛。不是「规范更完整」，而是「ese build 能生成一个能点、能跳转、能保存数据的页面」。语言的价值只有在第一次跑通时才能被证伪或证实。
  6. 开源前先定治理。符号冻结、RFC 流程、弃用周期三项写进 README，否则社区的第一个提案就会撞上「符号表能不能加」这个未定义问题。

08结论

ese 在语言设计维度已经完成了它的工作：符号体系自洽且经过四轮歧义攻击而站住，语义层覆盖了建站所需的绝大多数场景，v2.9 又把契约、边界与诊断三块补上。剩下的全部问题都归到一个根因——它还没有跑起来过一次。

因此本报告的最终建议只有一句：把下一版的力气全部投到实现上，用能跑通的最小站点来验收设计。设计已经足够好到值得被实现，但也已经好到无法再从纸面上继续改进。
