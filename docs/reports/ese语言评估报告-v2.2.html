ese 语言 v2.2 设计评估报告

评估对象：《ese语言规范-v2.2.md》 · 评估日期：2026-09-30 · 性质：v2.1 评估后的复查报告（第三次评估）

一、总体结论

一句话结论：v2.2 补齐了 v2.1 评估指出的全部 3 个高优先级问题，并一次性搭出路由、状态、组件库、测试、SSR 五大子系统——总分从 48/70 提升到 58/70。语言层语义至此基本齐备，规范已从「可以开工实现」进入「实现图纸完整」状态。新增子系统整体质量高（尤其状态管理的三级模型和 SSR「编译目标而非语言特性」的克制），但插槽机制、字典与插值的共用大括号、断言表达力三处存在值得实现前再推敲的设计细节。结论：评估阶段到此收尾，立即转入工具链实现，实现中暴露的细节边写边定。

四、v2.2 各子系统评估

优做得好的设计

  • SSR「编译目标而非语言特性」——本报告最高评价的一条。大量自创语言死在「为了 SSR 发明新语法」上；ese 的 ese build / ese serve 双目标 + 纯展示页零 JS 的设计，克制且正确。
  • 三级状态模型边界清晰——生命周期、可见范围一张表说尽；「全局状态只允许全局执行块修改、ese check 拒绝跨层赋值」把单向数据流做成了机器强制，比很多成熟框架的事后约定更硬。
  • 错误处理两级策略——「页面能出来（宽容）+ 算错了立刻看见（严格）」精准贴合低代码用户心理，且与 v2.1 评估推荐完全一致，避免了捕获语法带来的复杂度。
  • 符号冻结实战通过——六大子系统零新增括号对，全部用关键字 + 内置函数 + 编译目标实现，冻结声明不是空话。
  • 数据函数中文命名直觉良好——取第、长度、加入、包含，中文用户零学习成本；序号从 1 开始符合非程序员直觉。
高问题 1：插槽机制的表达力缺口

渲染 内容 只支持单个插槽。真实组件（如卡片：标题栏插槽 + 正文插槽 + 底部按钮插槽）需要多插槽。此外标准库 列表 的 {项}/{序号} 是组件私有的隐式变量，与用户作用域的关系未说明。建议 v2.3（或实现期间）定案：渲染 内容.头部 / 内容.正文 具名插槽方案，以及列表模板变量的作用域声明。

高问题 2：大括号双语义的工程风险

「文字内 {名字} 是插值、值位置 { "键":值 } 是字典」依赖位置区分语义。规范写清了规则，但这是全语言唯一一处「同一符号两种含义」，报错信息必须格外精准（用户在文字块里写了 { "a":1 } 会得到什么错？）。建议 ese check 对此设专项诊断：文字块内出现冒号即提示「插值只支持变量名」。另注意 [~ 遍历 用户 为 项 ~] 中 {项.键} 是「插值内点语法」，与纯变量插值的文法不同，需在 EBNF 中把 interpolation 的产生式扩为 { member-access }。

中问题 3：测试体系表达力偏薄

当前只有顶层 断言 与执行块断言，缺少：用例分组/组织（哪个测试属于哪个模块）、失败即停 vs 继续的用例级控制、异步/交互测试（点击按钮后界面变了吗）。v0.2 解释器阶段够用，v1.0 发布前建议补充「测试块」概念——同样不需要新括号，用 [> 测试 组名: … >] 复用执行块即可。

中问题 4：导航栏示例的嵌套字面量可读性临界

项目=[["首页","home"],["关于","about"]] 已经到了「一行看不懂」的边缘——这恰恰是 ese 要消灭的东西。标准库第一批组件的属性接口应避免嵌套字面量，建议 导航栏 改为插槽写法（[< 导航栏 > [(- 首页 -) 跳转 home] >] 风格），或在 ese-ui 里为它设计专用的声明式子语法。这条是标准库 API 品味问题，实现前定即可。

中问题 5：SSR 水合细节留白

「交互部分水合后由客户端接管」方向正确，但未说明：水合的粒度（整页还是逐组件）、服务端与客户端状态不一致时以谁为准、ese serve 的运行时语言（编译器本体用什么写）。这些不阻塞规范，但 v0.1 解释器选型时必须一并决定。

低问题 6：旧账两笔

运算符左结合仍未明文声明；打印 等基础内置函数仍未收录正式清单；异步预留声明依旧缺失。均为文档性工作，建议在 v2.3 一张附录里一并清掉。

六、结论与路线确认
