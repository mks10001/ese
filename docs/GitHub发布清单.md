# GitHub 发布清单（ese 语言）

> 用途：把 ese 规范与后续实现开源到 GitHub 之前，逐项核对。分为 **阻断项**（不做完不该公开）、**结构项**、**模板与自动化**、**传播与治理**、**最终检查表**五部分。
> 结论先行：这份项目最大的发布风险不是代码质量，而是**「看起来能用，其实不能跑」的误导风险**与**规范漂移带来的社区信任风险**。前四项阻断项都围绕这两点。

---

## 一、阻断项（不完成不要 push 到公开仓库）

### 1. 状态标注必须放在最显眼处

- [ ] README **第一屏**写明三项：规范版本 / 实现版本 / 实现状态
- [ ] 明确写出「**尚无可用实现，示例代码目前无法运行**」，而不是只在文末提一句
- [ ] 不出现「轻量」「极简」「已支持 X」等会让读者误判可运行性的措辞
- [ ] 所有示例旁标注「未实现，仅供参考」

**理由**：一个只有规范、没有实现的语言仓库，最大的失败模式是被当成可用工具或毕业设计模板引用。这会在半年内制造大量「跑不起来」的 issue，并消耗掉维护者的全部精力。

### 2. 个人隐私与内部信息清理

- [ ] 检索并删除文档、示例、注释中的**本机绝对路径**（如 `D:\...\项目\...`）
- [ ] 删除真实姓名、学校、群号、微信号、内网地址等身份信息
- [ ] 检查 `git log -p` 历史提交，确认早期提交里没有带隐私的草稿文件
- [ ] 若有敏感内容已进入历史：用 `git filter-repo` 重写后再推送（不要只删最新提交）
- [ ] 工作区草稿（如手写草案 txt、临时实验文件）**不要进仓库**——另建 `drafts/` 并加入 `.gitignore`，或干脆不上传

### 3. 密钥与授权材料绝不入库

- [ ] 若有授权码 / 签名校验相关的**私钥**（如 RSA 私钥、生成器脚本）：确认只保留在本地，公开仓库只放公钥与验签逻辑
- [ ] `.env`、`*.key`、`*.pem`、`token.json` 全部进 `.gitignore`
- [ ] 已推送过的密钥一律视为泄露，需要重新生成，而不只是删文件
- [ ] 开启 GitHub 的 **Secret Scanning** 与推送保护

### 4. 许可证必须先定，再公开

- [ ] 根目录放 `LICENSE`（GitHub 只识别根目录一个）
- [ ] 规范文档与实现代码**分别授权**：建议 `docs/` `spec/` 用 CC BY 4.0，`tools/` 用 Apache-2.0
- [ ] 在 README 明确写清「哪部分适用哪个许可」，并在 `docs/LICENSE` 附文档许可全文
- [ ] 未选许可前公开 = 默认保留全部权利，别人连 fork 与翻译都不被允许——这会直接杀死生态

## 二、仓库结构

```
.
├── README.md                  # 主 README（中文）
├── README.en.md               # 英文版（内容同步，不是逐句直译）
├── LICENSE                    # 实现代码许可（Apache-2.0）
├── CHANGELOG.md               # 与规范版本同步
├── CONTRIBUTING.md
├── CODE_OF_CONDUCT.md
├── SECURITY.md
├── .gitignore
├── docs/
│   ├── ese语言规范-完整版.md    # 唯一权威规范
│   ├── ese语言规范-v2.9.md      # 增量修订
│   ├── LICENSE-CC-BY-4.0
│   └── 评估报告/               # 缺陷评估、对比报告等历史文档
├── spec/                      # 机器可读单一数据源（规范的可执行化）
│   ├── grammar.ebnf
│   ├── keywords.json
│   └── diagnostics.json
├── rfcs/
│   ├── 0000-template.md
│   └── 0001-....md
├── examples/
│   ├── zh/                    # 中文模式示例
│   └── en/                    # 英文模式示例（两套不混用）
└── tools/                     # CLI、检查器、编辑器插件
```

- [ ] 文档文件名统一风格（中文名或英文 slug 二选一，不要混）
- [ ] 中文文件名可接受，但 README 里的链接要检查在 GitHub 上能否正确跳转（注意 URL 编码）
- [ ] 每份历史评估报告保留——它们记录了「为什么这样设计」，是新人理解成本最低的入口

## 三、模板与自动化

### 3.1 Issue / PR 模板

- [ ] `.github/ISSUE_TEMPLATE/bug_report.md` —— 仅用于**实现**缺陷（须附版本、`.bd` 片段、期望与实际）
- [ ] `.github/ISSUE_TEMPLATE/rfc_proposal.md` —— **语言变更必须走这条**，字段固定为：动机 / 语法草案 / 对现有代码的影响 / 是否破坏性 / 迁移方案 / 是否有替代方案
- [ ] `.github/ISSUE_TEMPLATE/spec_typo.md` —— 文档笔误的轻量模板
- [ ] `.github/ISSUE_TEMPLATE/config.yml` —— `blank_issues_enabled: false`，把开放讨论导向 Discussions
- [ ] `.github/PULL_REQUEST_TEMPLATE.md` —— 勾选项：是否改符号表（改了直接拒）、是否改生成产物（改了直接拒）、是否双语同步

### 3.2 CI（GitHub Actions）

- [ ] **单一数据源一致性校验**：由 `keywords.json` 生成的对照表与文档中的表做 diff，不一致就失败
- [ ] `grammar.ebnf` 可被解析器生成（防止文法写错）
- [ ] `examples/` 下所有示例通过 `ese check`（实现后就开启，先预留 job）
- [ ] 文档内部链接检查（历史文档互相引用很多）
- [ ] 全角/半角标点与行尾空格检查（可选，规范文档对格式敏感）

### 3.3 其它仓库文件

- [ ] `CONTRIBUTING.md`：把 README 的贡献节扩写，**第一条就是「符号表不讨论」**
- [ ] `CODE_OF_CONDUCT.md`：直接用 Contributor Covenant 2.1，不要自写
- [ ] `SECURITY.md`：披露渠道 + 响应预期
- [ ] `CHANGELOG.md`：按规范版本组织（v2.9 → …），破坏性变更单独标红
- [ ] `.gitignore`：`node_modules/`、`dist/`、`build/`、`.vscode/`、`*.log`、`.env`、`drafts/`

## 四、发布与版本策略

- [ ] **规范版本与实现版本解耦**：规范 `2.x`，CLI 从 `0.1.0` 起
- [ ] Tag 规则固定：`spec-v2.9`、`cli-v0.1.0`
- [ ] 每个 Release 说明必须含：规范版本 / 实现版本 / 实现状态 / 破坏性变更与迁移方式
- [ ] 破坏性变更**必须**附迁移工具（`ese fmt --migrate`），否则该版本不准发布——这条建议直接写进 CONTRIBUTING
- [ ] `main` 开启分支保护：需要 PR、需要 CI 通过
- [ ] 不使用 GitHub Releases 分发未验证的二进制（实现成熟前）
- [ ] 若做文档站：用 GitHub Pages 发布，源指向 `docs/`，并保证站内版本号与 tag 一致

## 五、社区、命名与治理

### 5.1 命名与法律

- [ ] 公开前检索 `ese` 在 GitHub / npm / PyPI / crates.io 的占用情况，确认不会与既有项目混淆
- [ ] 说明扩展名 `.bd` 的含义（**与网盘分享链接的 `.bd` 无关**，避免误读）
- [ ] 不要复制其它语言的文档文本或代码（**思想不受版权保护，文本受**）；借鉴请注明来源与差异
- [ ] 商标状态如实说明（「名称与扩展名商标状态未定，欢迎指出冲突」）
- [ ] README 不承诺未实现的功能（既误导用户，也可能构成虚假宣传）

### 5.2 治理公开化

- [ ] 把「三条硬规矩」写进 README 或 CONTRIBUTING：符号表冻结 17 对 / 三个单一数据源 / 破坏性变更必须附迁移工具
- [ ] `rfcs/` 目录 + RFC 模板就位，并在 README 指向它
- [ ] 明确弃用周期：次版本发弃用警告 → 下一个次版本破坏

### 5.3 社区设置

- [ ] Discussions 开启并分类：语法讨论 / 实现提问 / 展示 / 公告
- [ ] Labels 规划：`spec`、`impl`、`rfc`、`breaking`、`a11y`、`good-first-issue`、`wontfix`
- [ ] 语言政策写清：仓库主文档中文，英文 README 同步维护；但**语言本身两种模式互不互通**
- [ ] 维护带宽现实声明：solo maintainer、无 SLA、issue 可能长期不回复——提前写清比事后道歉好
- [ ] 对「加一个括号」类提案准备统一回复模板（附设计哲学第 6 条链接）

## 附：三条最容易踩的坑（来自本项目自身历史）

1. **破坏性修订没有迁移工具**。ese 的按钮定界符在 v2.5 → v2.8 四版内改了四次，每次都是「用户自己改代码」。开源后这类变更必须带 `ese fmt --migrate`，否则第一批用户会在第一次升级时流失。
2. **文档里的文法与关键字表手工维护多份**。一旦开两个以上消费者（解析器、检查器、文档、编辑器插件），手工同步必然错位。三个 `spec/` 数据源必须在公开前就位，哪怕内容是空的。
3. **把「设计完成」当成「产品可用」**。规范写得好会制造一种虚假的成熟感。README 的状态标注是唯一能对冲它的手段，务必写难看一点。
