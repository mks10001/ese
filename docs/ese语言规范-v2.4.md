# ese 语言规范 v2.4（增量）

> **本文档为 v2.3 的增量规范**：未提及的一切规则沿用 v2.2 / v2.3。
> v2.4 只做三件事——**① 异步能力预留声明；② 强化 `[ee]/[zz]` 的 pragma 定位；③ 明确两种模式互不互通。**

---

## 一、变更总览

| 类别 | 变更 | 性质 |
|------|------|------|
| 异步 | 预留 `等待`、执行块 `异步` 修饰、组件生命周期钩子三类语法位；当前一律按同步执行 | 预留声明（不实现） |
| 模式标记 | `[ee]/[zz]` 定位为编译指令（pragma）的完整约束：不进符号表、不可嵌套、独占一行、仅限顶层、一文件一模式 | 规则强化 |
| 模式互通 | **两种模式不互通**：同一构建单元内必须模式一致，跨模式 `引入` 一律拒绝 | 破坏性修订 |

---

## 二、异步能力预留声明（v2.4 新增）

### 2.1 为什么现在写这一句

ese 至今没有异步语义：执行块同步执行、`跳转` 同步生效、`等待` 不存在。但计时器、动画、数据请求终将需要异步。如果在 v3.0 临时发明语法，很可能破坏括号体系或「换行即结束」的既有语义。**v2.4 因此先划出三个语法位并冻结，不实现、不允许使用。**

### 2.2 预留语法位（冻结，当前使用即报错）

| 预留语法 | 形式 | 未来含义 |
|----------|------|----------|
| 等待语句 | `等待 3秒`（`wait 3s`） | 暂停当前执行块，其余界面不阻塞 |
| 异步执行块 | `[> 异步 名字 : … >]`（`[> async name : … >]`） | 声明该逻辑块为异步，内部可使用 `等待` 与网络请求 |
| 组件生命周期钩子 | `当 组件加载` / `当 组件卸载`（`on mount` / `on unmount`） | 组件挂载 / 卸载时触发 |

```
[! 以下写法在 v2.4 下均报错：功能未开放（v3.x） !]
等待 3秒
[> 异步 加载数据 :
  [@ "https://api.example.com/data" @]
>]
```

### 2.3 当前语义（务必明确）

- **所有代码同步执行，按源码顺序、换行即结束的既有规则运行。**
- 未开放任何并发、回调、Promise 类机制；组件内不存在生命周期。
- 预留语法位**不引入任何新括号对**——`等待` 是语句关键字，`异步` 是执行块修饰词，钩子复用执行块结构。符号表仍然是 17 对。

## 三、`[ee]` / `[zz]` 的 pragma 定位（v2.4 强化）

`[ee]` 与 `[zz]` **是编译指令（pragma），不是语言符号**。完整约束如下：

| 约束 | 规则 | 违例后果 |
|------|------|----------|
| ① 不进符号表 | 正式符号仍为 17 对；pragma 不参与任何容器/配对语义 | —— |
| ② 不可嵌套 | 不能作为内容被其他块包含，本身也不能包含内容 | 语法错误 |
| ③ 独占一行 | 行内出现 `<其他内容>[ee]` 或 `[ee]<其他内容>` 均为语法错误 | 语法错误 |
| ④ 仅限顶层 | 只能出现在文件的顶层位置，不得位于任何容器/组件/页面体内 | 语法错误 |
| ⑤ 一文件一模式 | 文件内首次出现的 pragma 决定该文件模式；之后再出现其他模式的 pragma 报错，重复同模式 pragma 为冗余警告 | 错误 / 警告 |

```
[zz]                                  [! 合法：顶层、独占一行 !]
[+ 组件 卡片
  [ee]                                [! 非法：出现在块内（违反 ④） !]
  [- 正文 -]
+]
```

**默认模式**：文件未出现任何 pragma 时，默认 `[zz]` 中文模式（向后兼容 v2.3 之前的一切文件）。

## 四、两种模式互不互通（v2.4 新增，破坏性修订）

### 4.1 规则

- 一个**构建单元**（一起编译部署的文件集合）内，所有 `.bd` 文件**必须模式一致**。
- **跨模式 `引入` 一律拒绝**：中文模式文件不得引入英文模式文件的组件或函数，反之亦然。ese check 报错并指明两文件的模式冲突。

```
[! 文件 A：中文模式 !]
[zz]
引入 "./english-card.bd" 的 WelcomeCard     [! 报错：模式冲突（A 为中文，被引入文件为英文） !]
```

### 4.2 设计理由与代价

**理由**：

1. **符号与标识符不变，但生态不必打通**——双语的本意是「两种母语用户各写各的」，不是「一套双语文档维护两遍」。不互通让文档、报错、测试各自单一语言，成本减半。
2. **避免混排地狱**：一个项目里中文组件名与英文组件名混用（`引入` 后调用 `WelcomeCard` 塞进 `[< 欢迎卡 >]` 风格的文件）会显著损害可读性——这正是 ese 最不能输的东西。
3. **构建产物确定**：不会出现同一个包里两种语言的关键字共存导致的构建期歧义。

**代价（必须承认）**：

- 中文社区与英文社区**不能共享组件库与第三方包**，标准库 `ese-ui` 需提供两套同构发布（关键字不同、接口相同）。
- 混合语言团队需要统一项目语言。

**未来出路（v3.x 规划，非现在实现）**：提供**源到源转换工具 `ese convert --to=ee`**，把整个项目的关键字机械翻译为另一模式（标识符不变）。两个生态的沟通只通过这个官方通道，而不是运行时互通。这也让「不互通」不至于成为永久性分裂。
