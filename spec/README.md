# spec/ —— 机器可读的单一数据源

本目录存放 ese 语言的**机器可读定义**。它与 `docs/ese语言规范-完整版.md`（人读规范）是同一份语义的两种呈现：

> **规范文档是给人读的，`spec/` 是给工具读的。两者不一致时，以 `spec/` 为准并修正文档。**

之所以必须存在这一层，是因为 ese 有一条硬性约束：**关键字与报错消息不得手工维护中英两份**（见规范 §16.4、§21.1）。`keywords.json` 与 `diagnostics.json` 是这条约束的唯一执行手段——VSCode 插件、`ese check`、运行时、`ese doc` 全部从这两个文件读取，禁止各自硬编码。`tools/src/` 里搜不到任何一句面向用户的报错文本，这是可复核的。

## 状态

**三个文件均已就绪**（2026-09-30，对应规范 v2.10 / CLI v0.1.0）。

| 文件 | 内容 | 规模 |
|------|------|------|
| [`grammar.ebnf`](grammar.ebnf) | 完整 EBNF 文法 + `@symbols` / `@reserved` 机器可解析区块 | 17 对正式符号，4 组预留符号不在文法中 |
| [`keywords.json`](keywords.json) | 中英关键字、pragma、内置属性、样式白名单、事件字段 | 50 条关键字 |
| [`diagnostics.json`](diagnostics.json) | 全部诊断码、中英消息模板、占位符登记、文本格式 | 50 个诊断码 |

### `grammar.ebnf`

从规范 §18 提取的完整文法，是 `ese check` 解析器的权威依据。

- 覆盖全部 17 对正式符号，**不含预留区**（`[b d]` `[u n]` `[q p]` `[@ @]` 解析即报 `ESE1005`）
- 含表达式优先级层级：`or-expr → and-expr → cmp-expr → arith-expr → term → unary → primary`
- 含 `SP` 终结符（按钮定界符内侧的空格是语法成份，非排版习惯）
- 顶部 `@symbols` 区块以固定格式列出 17 对符号，供 CI 计数校验

### `keywords.json`

- 每条关键字含：`id`、中形 `zh`、英形 `en`、语法位置 `position`、引入版本 `since`、状态 `status`
- `status` 三值：`active` / `reserved`（语法已冻结、当前使用即报错）/ `open`（已知缺口）
- 中英两形**必须同批增删**，不允许单侧存在

### `diagnostics.json`

- 码段：`ESE1xxx` 词法与语法 / `ESE2xxx` 静态检查 / `ESE3xxx` 运行时 / `ESE4xxx` 构建与工具
- 每条含：错误码、严重级别、中英消息模板、占位符列表、触发条件、`hint`（可选）
- 消息模板内的变量用占位符表示，由工具填充。**新增占位符必须先登记到 `meta.placeholders`**，否则 C3 校验失败

## 校验（CI 与本地同源）

```bash
node tools/src/cli.ts spec verify
```

四项断言：

| 编号 | 断言 | 说明 |
|------|------|------|
| **C1** | `grammar.ebnf` 中出现的关键字，全部存在于 `keywords.json` | 含 CJK 的字面量与长度 ≥ 2 的 ASCII 词均视为关键字；运算符、定界符、单字母（如按钮定界字母 `c`）视为结构性符号而豁免 |
| **C2** | 中英两形数量相等；整条词组无重复 | **唯一性作用于词组而非词元**——多词关键字（`引入 … 的 …` / `import … from …` 与 `引入 … 为 …` / `import … as …`）本就必须共享词元，按词元判重会把正确的表判成错的 |
| **C3** | 每条诊断的中英模板占位符集合一致、占位符已登记、编码符合 `ESExxxx` | |
| **C4** | `@symbols` 区块列出的正式符号对恒为 17 | 符号冻结的机器强制 |

三项建议（尚未自动化）：C5 规范文档关键字表与 `keywords.json` 的行数比对；C6 `grammar.ebnf` 中每个非终结符均可达（勘误 E-1 就是这一类缺陷）；C7 `examples/` 下全部 `.bd` 通过 `ese fmt --check`。

## 已记录的待定案

以下是编写数据源时发现的、**规范尚未回答**的问题。不是笔误，是真实缺口——留在此处而非就地发明，避免悄悄扩张语言。

| 编号 | 问题 | 影响 | 建议出口 |
|------|------|------|----------|
| **A-1** | 常用容器属性（`宽` / `居中` / `背景` / `间距` / `边框`）**只有中文形**，英文模式下的写法规范从未定义 | `[ee]` 项目的排版属性无标准写法，双语对等性出现缺口 | RFC：为这五个属性定英文形，并决定属性名是否也纳入「模式只切换词」的规则 |
| **A-2** | 输入框缺 `标签="…"` 时的严重级别未明确（媒体块缺 `替代` 定为警告） | 无障碍检查的严格度不确定 | RFC 或实现期定案；当前 `diagnostics.json` 中按 `warning` 登记并在条目标注 |
| **A-3** | `组件名` 与内置关键字同名时如何解析（如组件叫 `页面`） | 词法歧义 | RFC：建议禁止关键字作标识符，并在 `ese check` 报错 |
| **A-4** | `ese.json` 的英文模式字段名未定义（示例只用中文字段 `名称` / `模式` / `入口` / `ui`） | 与 A-1 同源 | RFC：清单字段建议固定为英文，不随模式变化 |

## 与规范文档的同步责任

`grammar.ebnf` 顶部的 `@symbols` 与规范 §3.1、§18 必须一致。**任何一方改动都要同时改另一方并跑 `ese spec verify`。** 勘误 E-1（`item` 的不可达产生式）就是这样被发现的：先写数据源，再回头对齐文档，缺陷无处可藏。
